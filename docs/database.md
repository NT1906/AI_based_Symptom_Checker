## Guest sessions and anonymous ownership (S1-KAV-4, idea § 10)

Per idea § 10, guest mode enables immediate triage without requiring sign-up:
- **Bearer Token Security:** When an anonymous session begins, `create_guest_session`
  generates a 32-byte URL-safe cryptographic token (`secrets.token_urlsafe(32)`).
  Raw tokens are returned directly to the client and **never** stored in the database.
  Only the 64-character SHA-256 hex digest is persisted in `guest_sessions.token_hash`.
- **Expiration:** Guest sessions expire after a configurable TTL (default 24 hours).
  The database enforces `expires_at > created_at`.
- **Assessment Ownership:** Assessments link to guest sessions via `guest_session_id`.
  An unauthenticated assessment possesses a `guest_session_id` and `consent_id`,
  with `user_id` set to `None`.
- **Account Claiming & History Transfer:** When an anonymous guest signs up or logs
  in after triage, `claim_guest_session(session, guest_session_id, user_id)`:
  1. Sets `guest_sessions.claimed_at` and `guest_sessions.claimed_by_user_id`.
  2. Reassigns ownership of all assessments in that guest session to the user (`assessment.user_id = user_id`).
  3. Prevents re-claiming an already-claimed guest session.
- **Deletions:** Foreign keys for `guest_sessions.claimed_by_user_id` and
  `assessments.guest_session_id` use `ON DELETE SET NULL`. If a user account is deleted,
  the session claim pointer clears; if an expired guest session is purged, assessments
  retain their historical consent integrity without hard cascades.

Password hashes are opaque and nullable. Auth must reject password login for a
NULL hash; seed accounts deliberately have no login credential. Hashing and
validation belong to the auth module. Never store plaintext passwords.

## History queries, pagination, and ownership filters (S2-KAV-4, FR-02)

Per FR-02, authenticated users can review their assessment history with efficient,
paginated querying and strict data ownership isolation:
- **Covering Index Optimization:** Queries on `user_id` ordered by `created_at` DESC
  are covered by the composite index `ix_assessments_user_id_created_at`.
- **Query-Level IDOR Protection:** Ownership filters operate directly in SQL
  `WHERE` clauses (`WHERE assessments.id = :id AND assessments.user_id = :user_id`),
  ensuring cross-user assessment records are never leaked or loaded into memory.
- **Unified Ownership Resolver:** `get_assessment_by_ownership` verifies access for
  either registered accounts or unclaimed guest sessions.
- **Rich Filtering & Lookahead:** `query_assessment_history` provides filtering by
  single or multiple states, timestamp bounds (`created_after`, `created_before`),
  configurable ordering direction, and optional relation eager loading (`selectinload`
  for messages, symptoms, and consent) to eliminate N+1 queries.
- **Accurate Pagination:** `count_assessments_by_user` enables exact page calculations
  matching active state and date filters.
- **Safe Account Erasure:** `delete_assessment_for_user` and `delete_assessments_for_user`
  enforce strict user boundaries during individual or bulk data deletion (DR-06).

No image column, doctor directory, prediction scores, or medical
recommendations are introduced. Structured symptom JSONB is S1-HAR-2.

## Migration and session interfaces

The migration is an explicit immutable table definition. Do not replace it with
`Base.metadata.create_all()`. Future schema changes require a new reviewed
revision. `downgrade` drops these tables and data; use only disposable databases.

The engine factory validates the psycopg driver and enables pool pre-ping and
hidden SQL parameters. Creating an engine does not connect immediately. Caller
code owns shutdown disposal. Repositories can use:

```python
factory = create_session_factory(engine)
with factory.begin() as session:
    # Repository operations: commit on success, rollback on failure, always close.
    guest_session, raw_token = create_guest_session(session)
```

`upgrade_database(engine)` passes a live connection to Alembic using
`Config.attributes["connection"]`. These patterns follow the official
[SQLAlchemy transaction documentation](https://docs.sqlalchemy.org/en/20/orm/session_basics.html)
and [Alembic connection-sharing cookbook](https://alembic.sqlalchemy.org/en/latest/cookbook.html).

## User Profiles & Clinical Context (S2-KAV-3, FR-02, idea § 10)

Per idea § 10 and FR-02, users may optionally save minimal clinical context to inform triage analysis without compiling an expansive medical dossier:
- **Data Minimization:** Coarse age bands (`child`, `teen`, `young_adult`, `adult`, `senior`) are used instead of exact dates of birth, strictly limiting personal identifying data per the DPDP Act 2023.
- **Clinical Sex:** Biological sex is captured solely for clinical risk calibration (`female`, `male`, `other`, `prefer_not_to_say`) with an optional `sex` alias.
- **Chronic Conditions:** Self-reported conditions (e.g. `["Diabetes", "Asthma"]`) are stored as structured JSON/JSONB text arrays.
- **Cascading Lifecycle:** The `profiles` table maintains a 1-to-1 foreign key to `users.id` with `ON DELETE CASCADE`. If an account is deleted, the health profile is purged immediately.

### Privacy & Compliance Invariants (DPDP Act 2023, DR-06, S2-HAR-7)
- **Zero PII Leakage:** The audit table strictly records operational metadata, model/engine lineages, and non-identifying telemetry. Freeform text, dialogue turns, patient names, and phone numbers are forbidden.

## History Query Optimization & pgvector Embeddings (S2-NIT-4, S2-NIS-7)

Owner: Nishith · Task: S2-NIT-4 · Issue: #160 · Requirements: NFR-01, FR-02, FR-03, FR-18, DR-02

Revision `0007_history_indexes_pgvector` delivers two major database tier capabilities:

### 1. History Query Indexing (FR-02, NFR-01)
- Adds composite covering index `ix_assessments_user_id_state_created_at` on `(user_id, state, created_at)`.
- Accelerates filtered queries in `query_assessment_history` and `list_assessments_by_user` (e.g. `WHERE user_id = :uid AND state = 'COMPLETED' ORDER BY created_at DESC`), enabling index-only scans for assessment history pagination.

### 2. Dense Semantic Vector Retrieval with pgvector (S2-NIS-7, DR-02)
- Provisions PostgreSQL `vector` extension (`CREATE EXTENSION IF NOT EXISTS vector;`).
- Adds `symptom_embeddings` table to store 384-dimensional dense sentence embeddings (`all-MiniLM-L6-v2`, L2-normalized) for ~700 items (100 canonical symptoms + 602 lay terms).
- **Strict Determinism (DR-02):** **No HNSW or IVFFlat index is created.** An exact linear scan over 700 rows executes in < 2 ms and guarantees that repeated nearest-neighbor queries return identical clinical symptom candidates.
- Pinned model revision tracking via `model_revision` and unique constraint `uq_symptom_embeddings_revision_phrase` on `(model_revision, phrase)`.
- Index `ix_symptom_embeddings_model_revision` on `(model_revision)` enables instant scoping to the active model commit.

| Column | Type | Nullable | Rationale / Constraint |
|---|---|---|---|
| `id` | `BIGSERIAL` | No | Autoincrementing primary key. |
| `symptom_id` | `VARCHAR(64)` | No | Canonical symptom ID (e.g. `chest_pain`). Check: non-blank. |
| `phrase` | `VARCHAR(256)` | No | Natural-language lay term or symptom name. Check: non-blank. |
| `model_revision` | `VARCHAR(64)` | No | Pinned Hugging Face commit hash of embedding model. |
| `embedding` | `vector(384)` | No | L2-normalized 384-dimensional dense embedding vector. |
| `created_at` | `TIMESTAMPTZ` | No | Server default `CURRENT_TIMESTAMP`. |

### 1. Complete 9-Table Data Dictionary

All primary keys use UUIDv4 (ORM-generated, native PostgreSQL `UUID`) except for `symptom_embeddings` which utilizes an autoincrementing 64-bit integer (`BIGSERIAL` / `BIGINT`) for performance in vector retrieval scans. ### 3. Data Integrity & Constraint Matrix

The system enforces data integrity through a layered approach: database-level constraints guarantee structural validity, while application-level guards enforce business logic and state machine transitions.

| Entity / Invariant | Enforcement Level | Mechanism | Failure Behavior |
|---|---|---|---|
| User Email | Database | `UNIQUE`, `CHECK (length(trim(email)) > 0)` | `IntegrityError` on duplicate or blank email. |
| Password Hash | Database | `CHECK (password_hash IS NULL OR length(trim(password_hash)) > 0)` | `IntegrityError` if empty string is supplied. |
| Consent Association | Database | `FOREIGN KEY ... ON DELETE RESTRICT`, `UNIQUE` | Cannot create assessment without consent; cannot delete consent while assessment exists. |
| Guest Session Expiration | Database | `CHECK (expires_at > created_at)` | `IntegrityError` if expiration is past or equal to creation time. |
| Guest Token Hash | Database | `CHECK (length(token_hash) = 64)`, `UNIQUE` | `IntegrityError` if token hash length != 64 chars. |
| Age Band Domain | Database | `CHECK (age_band IN ('child','teen','young_adult','adult','senior'))` | `IntegrityError` on invalid age category. |
| Biological Sex Domain | Database | `CHECK (biological_sex IN ('female','male','other','prefer_not_to_say'))` | `IntegrityError` on invalid biological sex value. |
| Assessment State Domain | Database | `CHECK (state IN ('START', ... 'COMPLETED'))` | `IntegrityError` on unauthorized state string. |
| Legal State Transitions | Application / Service | `AssessmentStateMachine` in `server/app/services/` | `InvalidStateTransitionError` (HTTP 400/409). |
| Message Turn Sequence | Database | `CHECK (position >= 0)`, `UNIQUE (assessment_id, position)` | `IntegrityError` on duplicate position or negative index. |
| Message Content Nonblank | Database | `CHECK (length(trim(content)) > 0)` | `IntegrityError` on empty or whitespace-only messages. |
| Message Role Domain | Database | `CHECK (role IN ('user', 'assistant'))` | `IntegrityError` on unauthorized role. |
| Symptom Uniqueness | Database | `UNIQUE (assessment_id, name)` | `IntegrityError` on duplicate symptom within assessment. |

| Audit Log Action Nonblank | Database | `CHECK (length(trim(action)) > 0)` | `IntegrityError` on blank audit action. |

### 4. DPDP Act 2023 & Lifecycle Policies

In compliance with India's Digital Personal Data Protection (DPDP) Act 2023, data retention (DR-06), and medical privacy principles:

1. **Anonymous Guest Session Purge (24h TTL):**
   - Guest sessions have a strict 24-hour expiration (`expires_at = created_at + 24h`).
   - A scheduled cleanup job removes expired guest sessions (`WHERE expires_at < now()`).
   - `assessments.guest_session_id` uses `ON DELETE SET NULL`: clearing expired guest sessions detaches ownership without violating historical consent or triage integrity.
2. **Right to Erasure (User Account Deletion, DR-06):**
   - User account deletion triggers `profiles` deletion immediately via `ON DELETE CASCADE`.
   - `guest_sessions.claimed_by_user_id` is automatically set to `NULL` via `ON DELETE SET NULL`, preserving guest session metadata without user linkage.
   - User assessments require deliberate repository cleanup via `delete_assessments_for_user(session, user_id)`: child records (`messages` and `symptoms`) are deleted transactionally prior to the parent assessment due to `ON DELETE RESTRICT` safeguards.
3. **Audit Log Preservation & Clinical Reproducibility (NFR-10):**
   - `audit_logs` maintains foreign keys (`user_id`, `guest_session_id`, `assessment_id`) with `ON DELETE SET NULL`.
   - When a patient requests account erasure, all direct links to their identity in audit records are cleared (`SET NULL`), while the clinical triage decision, model versions, deterministic risk engine tier, and rules fired are preserved for medical compliance and safety reviews.
4. **Zero Image / Binary Storage Invariant:**
   - No table in the database contains image columns, BLOBs, or binary media payloads.
   - Skin condition images uploaded for triage analysis are evaluated in-memory and discarded immediately; only the non-identifying CV model version (`cv_model_version`) is logged in `audit_logs`.
5. **Bearer Token Security Invariant:**
   - Raw bearer tokens are never persisted in plain text.
   - The database stores only the 64-character SHA-256 cryptographic hex digest (`token_hash`), preventing session hijacking even in the event of an offline database compromise.
